# Spec — v2 Functional: CRM Segments + Growth Actions

**Version:** 1.0
**Date:** 2026-07-04
**Companion docs:** `data-model.md` (v1.0) · `../prd.md` M3/M7
**Scope:** turn the accumulated customer data into revenue — segments, customer alerts, and **action lists with drafted messages that a human sends** from the business number. Precondition: months of v0/v1 data; segments over two weeks of history are astrology.

---

## 1. Segments

### 1.1 Definitions (all thresholds in settings — nothing hardcoded)

Computed nightly per customer (WhatsApp-channel identities with `customer_id`; anonymous iFood identities get volume analytics but no actions):

| Segment | Default rule (config) |
|---|---|
| `novo` | first order within last N₁ days (30) |
| `recorrente` | ≥ N₂ orders (3) AND last order within its own typical cycle × tolerance |
| `em_risco` | previously recorrente; days since last order > personal median interval × k (1.8) |
| `perdido` | days since last order > N₃ (90) |
| `vip` | top decile by trailing-12m revenue (min N₄ orders) |

- **Personal cycle** (median days between orders) beats global thresholds — a monthly customer isn't "em risco" after 3 weeks, a weekly one is. Global fallbacks apply below 3 orders.
- Segment history is stored (`customer_segment_snapshots`: customer, segment, computed_date) — transitions power both alerts and measurement.

### 1.2 API & front

`GET /segments` (definitions + counts) · `GET /customers?segment=` · customer detail gains: segment badge, personal cycle, favorite items (top by quantity), LTV. Front: `/clientes` gains segment filter chips + a small funnel widget (novos → recorrentes retention %).

## 2. Customer alerts (extends the v1 alert feed)

- **Transition alerts:** recorrente → em_risco (the money alert); batch-digested daily, not per-customer spam: "5 clientes recorrentes esfriando — ver lista".
- **Milestones (positive, keeps the tool pleasant):** novo → recorrente conversions weekly digest.
- Same `/alerts` feed + system-number delivery to Gil (owner gets only the weekly action list, §3 — don't flood the owner).

## 3. Action lists (insight → action, PRD principle #7)

### 3.1 The weekly "lista de reconquista"

Weekly job assembles an **action list**: customers `em_risco`/`perdido` (caps + cooldowns below), each with a **drafted PT-BR message** generated by LLM from: name, favorite items, typical order, time since last order, and a tone guide in settings ("caloroso, simples, sem cara de marketing, como a dona do negócio falaria"). Example (illustrative): *"Oi Maria, tudo bem? Faz tempo que você não pede as suas coxinhas! Essa semana a fornada tá saindo fresquinha — quer que eu separe um cento pra sexta?"*

### 3.2 Human-sends mechanics (the ban-risk firewall)

- Action list rendered at `/acoes`: customer, reason ("não pede há 34 dias, ciclo era 12"), draft message, and a **`wa.me/55…?text=<draft>` deep link** — one click opens the *business* WhatsApp with the message pre-filled; the human reviews, edits, and hits send **themselves**, from the number the customer already knows.
- The system **never** sends to customers. No exceptions. (Consent/anti-spam stance: relationship messages from the known business number, low volume, human-sent — and a `do_not_contact` flag on customers, respected by list generation, set on any opt-out.)
- Each action row: status `sugerida → enviada (human marks, one tap) → respondeu / pediu / sem_resposta` (auto-inferred when a new order lands within the window; response manually markable).

### 3.3 Guardrails (settings)

Max contacts/week (default 10 — it's a family operation, not a call center) · per-customer cooldown (default 45 days) · `do_not_contact` respected · quiet hours irrelevant (human sends when convenient).

### 3.4 Measurement (close the loop or it's theater)

- Attribution: order within N days (14) of an `enviada` action → action marked `converteu`, revenue attributed (first order only).
- `/reports/actions?from&to`: sent, response rate, conversion rate, attributed revenue, by segment. This is the "sell more through augmented data" scoreboard — if it doesn't pay, we stop doing it and the data says so honestly.

### 3.5 API

`GET /action-lists/current` · `POST /action-items/{id}/mark` (enviada/resposta/skip+reason) · `POST /action-items/{id}/redraft` (regenerate message with optional instruction) · `GET /reports/actions`.

## 4. Owner experience

The owner's entire v2 surface is one weekly WhatsApp message (template): "Lista da semana pronta: 7 clientes pra chamar — abra aqui: <link>/acoes" plus the `/acoes` page with huge buttons: draft → [Abrir conversa] → [Marcar enviada]. Nothing else changes for them.

## 5. Acceptance criteria

1. Segments recompute nightly; a customer with 4 orders every ~10 days becomes `em_risco` at ~18 days silent, not at a global threshold.
2. Action list never includes `do_not_contact`, cooldown-active, or over-cap customers (property-tested against generated fixtures).
3. Every draft opens correctly pre-filled via wa.me deep link (URL-encoding torture-tested: emoji, accents, line breaks).
4. An order arriving 5 days after `enviada` auto-marks `converteu` and attributes revenue exactly once.
5. `/reports/actions` conversion math verified against fixtures; zero-action months render an honest empty state, not zeros dressed as insight.
6. The system provably cannot message customers: no code path sends outbound to any number outside the allowlist (test asserts the send-gateway allowlist guard).
7. Segment thresholds edited in settings take effect next recompute without deploy.
